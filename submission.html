Set the time range before you count anything.

The telemetry in this lab runs from 2026-03-25 to 2026-09-30. A fresh Discover page opens on “Last 15 minutes” and will show you nothing at all. Set the time range picker to the whole window first, and do the same on Security → Alerts, or every count you take is wrong.

Times are stored in UTC; Kibana prints them in your own timezone.

Read the clock times off your own screen and judge gaps between events, not absolute values. A timezone shift moves every time by the same amount, so a conclusion built on intervals survives any timezone and one built on a clock time may not.

One query-language note before you start.

This build of Elasticsearch does not accept the short field: ("a" or "b") spelling in the KQL bar, and it has no [from TO] date ranges in KQL either — write @timestamp > "2026-03-25" instead, and repeat the field on each side of every or. Where a detection rule's own query is shown to you on the Rules page it is written in the portable form, for exactly that reason.

4 · The detection rules

Five rules are installed and visible under Security → Rules; their alerts are on Security → Alerts. Read each rule's query, severity and risk score. Several of them are there to be reasoned about rather than obeyed, and your answer must say, rule by rule, whether it would have caught this and why.

How you are marked

Marks are for evidence, ordering and exclusions, not for naming a technique. A report that names three techniques correctly and dates nothing scores below one that names none and dates everything. Equally, a report that opens on the Alerts page and reports whatever fired there scores very low, and a confident answer to something these logs cannot show is marked wrong.
